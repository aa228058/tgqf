# TG Manager 产品需求与技术基线 V1.0

> 本文是项目长期有效的产品需求、技术架构和验收基线。后续开发、测试、部署以此为准。需求确认不代表功能已经实现；实现状态只能依据代码、自动化测试和端到端验收更新。
>
> 仓库： https://github.com/aa228058/tgqf  
> 产品：TG Manager  
> 版本：V1.0（需求整理完成，待统一开发）

## 1. 产品定位与总原则

基于 Telegram 普通用户账号 MTProto 的多租户网页管理平台，不是 Bot 管理后台。

- 租户业务数据严格隔离；公共群组总库是全系统共享的一份数据。
- HTTP API 与 Telegram Worker 分离；每个 Telegram 账号独立 MTGo client/运行上下文，避免单账号异常影响其他账号。
- 仅处理用户明确授权且 Telegram 隐私设置允许的对象，尊重用户意愿及适用法律。
- 遵守 Telegram 平台限制、FloodWait 和速率限制；不得通过轮换账号、代理或并发方式规避限制。
- 自动联系必须具备去重、频率限制、每日上限、失败冷却、停止联系/退订处理和审计。
- 只监听功能启用后的新消息；不扫描、不回溯历史聊天消息。
- Session、代理凭据、Telegram API 凭据加密或安全保存，不通过普通前端接口暴露。
- V1 不开发独立群发模块、群发页面或独立群发任务；关键词命中后的规则化消息处理能力仍然保留。

## 2. 已确认技术架构

### 2.1 技术栈
- 前端：Next.js、React、TypeScript。
- UI：Tailwind CSS、shadcn/ui。
- 后端：Go（明确覆盖早期草稿中的 Python FastAPI）。
- Telegram：MTProto，使用 `github.com/mtgo-labs/mtgo`（明确覆盖早期草稿中的 Telethon 和 README 中过时的 gotd 描述）。
- iOS 设备资料：`github.com/mtgo-labs/device-manager`。
- 数据：PostgreSQL。
- 缓存、队列和事件分发：Redis。
- 实时通信：WebSocket。
- 部署：Ubuntu VPS、Docker、Nginx、HTTPS。

### 2.2 MTGo + device-manager 约束
1. Telegram 普通用户账号连接统一使用 MTGo/MTProto，不使用 Bot API、Telethon。
2. 每个账号使用独立 MTGo client/运行上下文；API 与 Telegram Worker 分离。
3. 设备资料必须由 device-manager 自动生成 iOS profile（设备型号、系统版本等），禁止手工随机拼接参数。
4. 设备资料按 account ID 稳定生成，同一账号固定使用；必须持久化实际生成的 profile，服务重启、断线重连不得随机变化。
5. Worker 启动时读取已保存 profile 并应用到 MTGo config。旧账号需要有安全、幂等的 profile 补齐迁移。
6. MTGo/device-manager 升级必须验证配置兼容性、Session 兼容性和登录恢复。
7. Telegram API ID/Hash、Session、代理密码不得进入前端响应、日志或公开导出。

## 3. 用户、租户、卡密授权

### 注册登录
- 账号密码注册、登录。
- 同租户允许手机、电脑等多个设备同时在线。
- 修改密码后撤销其他设备会话，当前设备会话保留。
- 所有业务查询从认证上下文取得 tenant_id，不信任客户端传入。

### 卡密与超级管理员
- 超级管理员生成一次性卡密；一张卡密只能激活一次，可包含授权期限。
- 支持续费卡密、禁用卡密、查看激活记录。
- 超级管理员可创建、启用、禁用、删除租户；设置账号数量上限、授权有效期；查看租户使用情况。
- 超级管理员拥有独立后台和全局运维权限。

### 到期/禁用
- 租户到期或被禁用时，立即停止其后台任务并禁止继续业务操作，保留原有数据。
- 续期/解禁后，旧任务保持暂停，由租户检查后手动恢复，不自动续跑。
- 停止过程要安全落库，避免恢复时重复执行已成功操作。

## 4. Telegram 账号管理

### 登录和状态
- 手机号验证码登录、二维码登录、批量手机号登录。
- Session 文件导入、批量 Session 导入。
- 支持两步验证密码处理。
- 每账号记录登录状态、连接状态、代理状态、异常原因、登录失败原因、最近连接情况。
- 支持分组、标签、搜索、批量选择、资料导出、单独断开/重连。

### 代理管理
- 每账号独立代理；支持全局默认代理，新账号继承默认值，之后可单独覆盖。
- 支持 SOCKS4、SOCKS5、HTTP、HTTPS，以及地址、端口、用户名、密码。
- 支持代理检测和连接状态监控；检测结果需区分 TCP 可达、代理认证成功、Telegram 实际连接成功。
- 凭据加密保存，普通 API 不返回密码或密文。

### 批量修改资料
- 支持批量修改头像、姓名、个人简介。
- 支持统一资料应用，也支持为不同账号设置不同资料。
- 所有批量操作进入任务中心，记录每账号成功、失败及原因，并遵守平台频率限制。

### Session 和设备资料
- Session 加密存储，不通过普通前端 API 暴露。
- device-manager 自动生成 iOS 设备资料，按账号稳定、持久化，并应用到 MTGo。
- 重连和重启不重新随机生成 profile。

## 5. 公共群组资料总库（全系统共享）

总库是全系统共用的一份公共数据，不是每个租户独立维护。所有租户按权限查看和使用。

### 字段
- 群组名称、Telegram 群组 ID、头像。
- 公开用户名及链接、私密邀请链接、群组来源链接。
- 群组类型（公开/私密）。
- 默认发言权限（自由发言/仅管理员发言/待检测）。
- 成员数量、链接有效性、群组状态。
- 最近检测时间、首次发现时间、最后更新时间、发现来源。
- 贡献租户/账号和多来源关系。

### 管理规则
- Telegram 群组 ID 是主要去重键；自动去重、合并重复群组的链接和来源。
- 支持搜索、类型/发言权限/链接状态/成员数筛选、批量检测、TXT/CSV/Excel 导入导出。
- 租户可以贡献资料，但不能手动编辑或删除公共记录。
- 系统采集的信息可以更新和合并，保留来源及审计记录。
- 群组默认发言权限与当前账号自身权限分开存储。某账号被禁言不能推断群组仅管理员发言。
- 现有租户级聊天观察数据不等于全局公共总库；需设计全局群组实体及租户贡献/来源关联。

## 6. 群链接自动采集器

### 来源
- 已登录账号加入的群组和频道。
- 已登录账号收到的新私人消息。
- 租户指定且账号有权访问的其他群组和频道。

### 行为
- 实时监听新消息，识别 Telegram 群组链接、公开用户名链接和私密邀请链接。
- 提取群组资料、检测链接状态和群组默认发言权限，去重后进入公共总库。
- 支持 `t.me/username`、`t.me/+邀请码`、`t.me/joinchat/邀请码`。
- 每种来源可独立开启/关闭。
- 只采集采集功能启用之后到达的新消息；不扫描、不回溯、不补齐历史消息。
- 无法确认状态时标记“待验证”，不得直接判定失效。

## 7. 自动加群

- 支持公开群直接加入、私密邀请链接加入、需要管理员批准的入群申请。
- 跟踪申请状态，获批后更新账号加入状态。
- 从公共群组总库选择目标，选择单个或多个账号；每个账号可设置加入数量上限，同一群可分配多个账号。
- 展示每账号加入进度、成功/失败和失败原因。
- 普通异常可等待当前账号恢复、暂停等待人工处理、失败重试；备用账号只能用于正常调度，不得用于规避限制。
- Telegram FloodWait 必须遵守服务端要求的等待时间，不得轮换账号绕过限制。
- 任务具备暂停、恢复、取消、幂等控制和完整操作记录。

## 8. 关键词监听

- 每租户可创建多套独立规则，可启用、暂停、编辑、删除。
- 每套规则可配置监听账号、群组/频道、关键词、排除词、匹配方式、消息类型、用户资料字段、命中动作。
- 匹配方式：精确、包含、正则；用户名、昵称、群名字段可独立启停。
- 支持排除词；组合逻辑支持 OR、AND 和分组组合。
- 消息类型：文字、图片、视频、文件、语音、视频消息、相册及其他可识别类型。
- 只监听规则启用后的新消息，不扫描历史消息。

## 9. 关键词命中后的自动处理

私聊和群组流程必须分别配置、独立执行，互不影响。

### 私聊动作
- 按租户配置顺序发送文字、图片、视频、文件、语音、圆形视频、相册、文字与媒体组合消息。
- 联系人卡片必须使用 Telegram 原生联系人消息能力，不得用图片或文字模拟。
- 可配置 Telegram 原生一对一语音呼叫请求。V1 范围仅发起呼叫并触发目标端 Telegram 原生来电/响铃提示；不要求接听后的双向音频或对话。必须验证 Telegram 接受呼叫请求、目标端实际出现原生来电提示及状态回写；不能以文字邀请替代，也不得把响铃伪报为通话已接通。
- 不另设产品层额外授权白名单流程，但这不豁免 Telegram 隐私设置、用户意愿、明确授权和适用合规要求；不得向不允许联系的对象发起私聊或通话。
- 私聊任一动作失败后，停止该次私聊流程后续动作并记录失败原因。

### 群组动作
- 命中后在原群组中执行独立配置的回复/媒体动作。
- 群组处理不受私聊动作失败影响。
- 记录每次执行结果。

### 技术验收
- 联系人卡片需验证 MTProto 原生联系人消息实际发送与接收。
- 原生语音呼叫仅发起：验证 Telegram 接受呼叫请求、目标端原生来电/响铃提示及状态回写；不要求接听后的密钥协商或音频收发。未通过真实双账号响铃验收前标记“待真实环境验证”，不得宣称通话已接通。

## 10. 任务中心

所有批量操作和自动化任务统一进入任务中心。

### 状态
等待执行、正在执行、暂停中、已完成、部分失败、执行失败、已取消。

### 实时信息
总量、成功数、失败数、当前执行账号、每账号进度、当前执行内容、失败原因、重试次数。

### 控制与闭环
- 暂停、恢复、取消、失败重试。
- 实时日志和历史执行记录。
- 生命周期：创建 → 分配账号 → 执行 → 记录结果 → 异常处理 → 完成或等待人工处理。
- 断点恢复、幂等控制，避免恢复时重复执行已成功操作。
- WebSocket 实时推送状态和进度。
- 租户到期/禁用时安全暂停相关任务。

## 11. 数据、日志、监控、备份

### 数据
保存账号资料、公共群组资料、监听规则、命中记录、自动处理记录、任务记录、操作日志、账号与群组关系。提供可配置的数据保留期限；重要操作保留审计。

### 超级管理员监控
服务器 CPU、内存、磁盘；PostgreSQL、Redis；Worker 运行状态；Telegram 账号连接；代理异常；后台任务异常。

### 备份恢复
数据库定期备份；Telegram Session 加密备份；备份文件不可公开访问；支持恢复；关键数据变更留审计记录。

## 12. 页面与导航

租户端页面功能范围：控制台/工作台、账号管理、代理管理、群组总库、链接采集器、自动加群、关键词监听、自动处理规则、任务中心、日志记录、内容模板、系统设置。

超级管理员端：租户管理、卡密管理、授权管理、系统监控、公共群组总库管理、系统配置、数据备份、审计日志。

前端具体导航层级、桌面和手机布局、交互规范，以同目录的 `FRONTEND_PLAN_V1.md` 为准。不得将独立群发功能加入导航或开发范围。

## 14. 明确不开发的功能与决策

- V1 不开发独立群发模块、独立群发页面、独立群发任务。
- 关键词命中后的自动处理仍需具备规则化消息发送能力。
- 不扫描历史聊天消息，不回溯旧消息。
- 不为每个租户建立独立群组总库。
- 租户不能手动编辑或删除公共群组资料。
- 不额外增加产品层关键词命中白名单流程；仍须尊重隐私设置、用户意愿和适用合规要求。
- 不把原生来电请求替换为文字邀请。
- Telegram FloodWait 不得通过切换账号规避。

## 15. 开发阶段顺序

1. 基础系统：注册登录、卡密、多租户、超级管理员、数据库和隔离。
2. Telegram 账号管理：单/批量登录、Session、设备资料、代理、资料、批量修改。
3. 公共群组总库：全局数据模型、导入、去重、合并、搜索、筛选、检测。
4. 新消息链接采集：实时监听、链接识别、资料提取、自动入库。
5. 自动加群：多账号任务分配、申请跟踪、异常处理。
6. 关键词监听与自动处理：规则编辑、匹配组合、私聊/群组动作、联系人卡片、语音通话专项验证。
7. 任务中心：实时日志、任务控制、断点恢复、失败处理（底层任务机制应提前支撑各阶段）。
8. 集成测试和部署：多租户、并发、稳定性、安全、备份恢复和正式部署。

## 16. 需要持续跟踪的技术风险

- Telegram 原生来电请求不是普通消息发送功能；V1 仅专项验证呼叫请求、目标端响铃和状态回写，不包含接听后的双向音频链路。
- 批量登录时各账号验证码、2FA 和登录状态必须独立处理。
- 私密群邀请链接可能需要已登录且有权限的账号验证。
- 自动加群、资料修改必须遵守 Telegram 操作限制与 FloodWait。
- 多账号并发需控制连接数、任务队列和资源占用。
- 公共群组全局模型必须与租户贡献来源隔离设计。
- 设备资料必须真正持久化，而不只是每次按账号 ID 重新计算。

## 17. 当前项目状态声明

需求规格 V1.0 已整理，进入统一开发准备阶段。本文是需求基线，不是实现完成证明。每个模块的状态（未开始/进行中/已实现/已测试/待专项验证）必须由代码和测试证据维护。普通实现细节由开发方负责合理设计，不为常规技术选择反复打断产品确认。
