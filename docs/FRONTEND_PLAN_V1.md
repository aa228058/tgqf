## 1. 已确认的主导航

租户端桌面主导航：
1. 工作台
2. 账号管理（包含账号列表、代理管理、账号分组、设备资料）
3. 消息管理
4. 群组管理
5. 运行状态与日志
6. 系统设置
7. 管理后台（仅管理员可见）

手机端底部固定导航：
- 工作台
- 账号
- 消息
- 更多

手机端其他功能收进“更多”；代理管理不单独占用底部导航入口。

**范围边界：群发功能不在规划范围内。** 不添加群发页面、独立群发任务或相关导航。

## 2. 整体布局

### 桌面端
- 固定左侧导航栏 + 顶部栏 + 主内容区。
- 顶栏显示产品名称、连接/在线状态、用户菜单等。
- 主内容区按页面呈现卡片、表格、筛选器、详情抽屉和操作弹窗。
- 账号管理内部采用二级导航/标签：账号列表、代理管理、账号分组、设备资料。
- 管理后台仅超级管理员可见；普通租户用户不得看到入口，也不能通过 URL 绕过权限。

### 手机端
- 底部固定四入口：工作台、账号、消息、更多。
- “更多”收纳群组管理、运行状态与日志、系统设置、管理后台（仅管理员）等。
- 列表在窄屏改为卡片；复杂表单使用全屏页或底部抽屉；危险操作需二次确认。
- 适配手机和电脑，不让桌面表格直接缩小挤压。

## 3. 页面规划和交互

### 3.1 工作台
展示真实数据，不得填充演示假数据：
- 账号总数、在线账号、异常账号。
- 账号连接概况与异常提醒。
- 最近登录、连接和运行事件。
- 待处理消息数量。
- API、Worker 等真实可获得的运行状态。
数据尚未接入时显示加载、空状态或“暂不可用”，不伪造指标。

### 3.2 账号管理

#### 账号列表
- 展示头像、名称、手机号、分组、标签、登录状态、连接状态、代理状态。
- 支持搜索、分组筛选、状态筛选、分页、批量选择。
- 操作：导入/登录、断开、重连、资料编辑、导出。
- 登录入口：Telegram 扫码登录、手机号验证码登录、Session 导入；批量登录/批量导入按后端能力逐步接入。
- 扫码登录：二维码、过期时间、刷新、取消、成功/失败状态和错误原因。
- 手机号登录：手机号、验证码、两步验证密码的分步交互；每个账号登录流程相互独立。

#### 代理管理
- 添加/编辑代理：协议、地址、端口、用户名、密码。
- 检测代理连通性并明确结果含义。
- 为账号绑定/解除代理；查看代理绑定账号。
- 删除前检查是否仍被账号使用。
- 支持全局默认代理和账号单独覆盖。
- 密码字段不得回显明文。

#### 账号分组
- 创建、重命名、管理分组。
- 将一个或多个账号加入/移出分组。
- 提供空状态、删除确认和分组筛选联动。

#### 设备资料
- 展示账号对应的 device-manager iOS 设备资料。
- 只读展示为主，明确资料生成/持久化状态。
- 不提供随机生成或手工拼接设备参数的交互。
- profile 未保存或未加载时展示异常状态，不显示伪造资料。

### 3.3 消息管理
统一消息收件箱，展示符合后端采集规则的新消息：
- 支持按账号、群组/聊天、文字/媒体等条件筛选。
- 消息项展示发送方/聊天、内容预览、媒体类型、时间、处理状态。
- 点击消息进入对应聊天上下文并回复（以实际后端接口能力为准）。
- 左滑或操作菜单标记已处理；已处理消息从默认未处理列表消失。
- 不添加独立测试快捷回复按钮。
- 不混入普通群聊非目标消息、广播频道消息或自己发出的消息。
- 筛选条件应在后端入库阶段生效，前端筛选仅是展示层补充。
- 仅展示新消息，不提供历史消息扫描/回溯入口。

### 3.4 群组管理
- 群组列表展示头像、名称、类型、用户名/链接、成员数、链接状态和来源等已存在字段。
- 支持搜索、按类型/状态筛选、分页。
- 查看群组资料及关联账号（以实际数据权限和 API 支持为准）。
- 产品规格中的“公共群组总库”必须体现全系统共享语义；租户端只允许查看、使用和贡献，不提供手工编辑/删除公共记录的入口。
- 群组默认发言权限和账号在群内的个人权限分别展示。

### 3.5 运行状态与日志
先展示后端真实提供的数据：
- API 服务状态。
- Telegram Worker 状态。
- 账号连接状态。
- 最近错误、运行日志、任务异常。
- 连接异常提示。
只有后端提供可靠控制接口后，才展示任务暂停/恢复/取消等按钮；不制作无效按钮。

### 3.6 系统设置
- 个人资料和密码修改。
- 浅色/深色主题。
- 通知设置（后端支持时持久化）。
- 登录安全设置和会话管理（按实际 API 能力开放）。

### 3.7 管理后台（仅超级管理员）
- 租户管理：创建、启停、删除、账号上限、到期时间、使用情况。
- 卡密管理：生成、查询、禁用、激活记录。
- 授权管理。
- 系统监控。
- 公共群组总库管理（遵循系统权限和审计）。
- 系统配置、数据备份、审计日志。
- 普通租户不得通过前端路由或直接 API 请求访问管理能力。

| 项目 | 规范 |

| 产品风格 | 现代 SaaS，简洁、清晰、信息层级明确 |
| 默认主题 | 浅色 |
| 备用主题 | 深色 |

## 5. 页面/API 对接原则

- 每个页面都要标注数据来源、接口、字段、权限、加载状态和错误状态。
- 现有 API 能力与规划页面必须区分，不得将“计划接口”描述为“已实现接口”。
- 后端尚未提供接口时，页面先完成设计规格和交互稿，不做假数据驱动的伪功能。
- 所有租户业务请求依赖服务端认证上下文和租户隔离；前端隐藏入口不构成安全边界。
- 任务进度和实时状态优先使用 WebSocket；若某接口当前使用 SSE，应明确记录协议差异。
- 表单校验、请求中状态、防重复提交、失败重试和危险操作确认应统一设计。

## 6. 当前已知前后端差距（基于最近一次仓库检查，需随代码更新）

- 前端已有 Next.js/React/TypeScript 项目基础，但尚未形成完整管理后台页面。
- 后端已有注册/登录/激活/登出/改密码、超级管理员租户和卡密基础接口。
- 账号管理已有基础 CRUD 和二维码登录能力。
- 代理已有账号绑定/加密等基础能力；独立代理 CRUD、检测等能力需按实际路由和测试再核实。
- 消息汇总已有后端数据/事件相关基础实现；前端统一收件箱尚未完成。
- 当前群组观察数据与产品要求的全系统共享公共群组总库不是同一概念，需补全局数据模型。
- 完整运行监控、WebSocket 任务中心、完整批量登录、Session 文件导入、批量资料修改等需按接口逐项核实和补齐。
- 不得因页面设计文档存在而宣称页面/API 已完成。

## 7. 前端实施顺序

1. 全局框架：导航、主题、响应式布局、登录和权限。
2. 工作台。
3. 账号管理：账号列表、扫码/手机号登录、Session 导入、代理、分组、设备资料。
4. 消息管理：筛选配置、消息列表、回复上下文、标记处理。
5. 群组管理。
6. 运行状态与日志。
7. 系统设置。
8. 管理后台。
9. 全部页面统一检查、无障碍与响应式检查，再执行完整构建和集成验证。

**实施进度：第一阶段全局框架已开始实现。** 桌面侧栏、顶部栏、手机底部四入口/更多菜单、浅色/深色主题、登录会话恢复和超级管理员导航可见性已进入开发分支；现有任务中心作为第一个已接入页面保留。其余页面继续按顺序接入真实接口，不以占位页面伪造业务数据。
