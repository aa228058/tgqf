> 本文是项目当前唯一进度台账。产品规则以用户确认的《整体架构与后续开发规划》为准；本文只记录代码证据、测试证据和未完成事项。需求写入文档不等于功能完成。

## 0. 不可变架构原则

1. 租户自主配置业务策略、业务配额、执行间隔、时间窗口、账号分配和任务策略；未配置业务配额时，不得套用隐藏的系统业务上限。
2. 系统只执行技术与平台安全保护：授权检查、幂等、资源保护、异常暂停、审计，并严格遵守 Telegram FloodWait；不得通过账号轮换规避限制。
3. 账号真实群成员关系、全局共享群组资料、租户贡献归属是三类不同数据，不得因公共群组去重而破坏账号成员关系。
4. 租户数据按 tenant 隔离；公共群组目录全局共享只读，租户可贡献和导出；超级管理员拥有全局管理能力且操作留审计。
5. 业务共用账号资源、群组资源、群组选择器、策略配置和任务调度能力；不为每个业务重复实现一套。
6. 每个模块按 DB → API → 业务逻辑 → 权限 → 前端 → 联调 → 自动化测试完成闭环。UI 不能伪造后端能力。
7. Telegram 自动化只处理授权且允许访问的对象；遵守平台规则、用户意愿与适用法律。不得实现规避限制或无差别骚扰。

## 4. 现有实现与关键风险

- 数据库已有 67 个迁移；涉及账号、全局群组、加群、关键词动作、多媒体、语音呼叫、任务公平调度、outbox、审计/系统配置等。优先扩展现有实现，避免另建平行体系。
- Go 格式检查当前采用增量门禁：强制检查新增加的 Go 文件；历史代码仍存在未格式化文件，不能宣称全仓库已 gofmt。后续修改旧文件时应逐步格式化对应文件。
- 已有加群任务和关键词动作队列并不自动等于“统一任务调度中心”；需要通过统一任务/目标/执行结果模型逐步收敛。
- 已有关键词多个动作能力不自动等于“可编排动作链”；需要验证数据库是否支持动作顺序、独立状态、重试和动作账号授权。
- 已有 account_limit 默认值 5 并在账号创建时强制校验，与“取消系统预设账号业务配额”存在潜在冲突，列为架构决策阻塞项。
- 账号分组字段 group_name 不等于账号群组成员关系；公共群组库也不等于账号实际加入群组列表。三者必须分开。
- README/旧产品规格写有 V1 不开发独立群发模块；本项目仍遵守平台限制和授权联系边界。若后续要调整产品范围，应先更新产品规格，不能直接偷偷增加独立群发流程。
- Telegram 语音呼叫只按已确认范围验收：能发起并触发目标端原生来电提示、记录状态；不要求接听后双向通话。不得宣称未验证链路已可用。

## 5. 待办维护规则

1. 每次完成一个模块，在同一 PR 中更新本文件的状态、测试证据、遗留项。
2. PR 合并前标记“代码已实现待验证”，合并且自动化测试通过后才可标记“验证通过”；需要真实 Telegram 账号的专项项目必须另行标记“待专项验证”。
3. 发现跨模块架构问题时，登记在“关键风险”，不要在局部模块偷偷引入第二套模型。
4. 新增功能先查现有 API、表、队列和前端组件；优先复用和迁移。
5. 禁止把未实现的页面、模拟数据、仅有数据库字段或仅有 API 当成闭环。
