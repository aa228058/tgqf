# 四大核心模块闭环实施方案

基线：`main`（实施分支：`feat/four-core-modules-closure`）

本方案覆盖账号管理、群组库、自动加群、监控系统；目标是让租户从群组选择到任务执行、冷却恢复、结果回流形成完整闭环。

## 1. 账号管理

- 统一账号状态：正常、待登录、登录失效、受限冷却、异常、停用。
- 展示账号健康、代理连通性、最近错误、冷却截止时间、当前任务和实际已加入群组。
- 账号操作必须有租户边界和审计记录；敏感会话凭据不得返回前端。
- 实际群组同步应可追踪，支持增量/全量同步及失败重试，不把“同步失败”误报为“没有群组”。

## 2. 群组库

- 统一管理公开群组和私密邀请链接，保留来源、发现时间、有效性、群组类型、加入/审批状态。
- 支持搜索、筛选、去重、分页跨页选择、批量导入导出。
- 选择群组后直接“创建批量加群任务”，将选中目标快照写入任务，避免创建后群组库变化影响任务。
- 对私密邀请链接先校验可用性；失效、已撤销、已加入、需要审批等状态必须分别展示。

## 3. 自动加群

- 一次创建一个批量任务，任务下有 N 条独立目标记录；每条记录具备状态、执行账号、尝试次数、下次可执行时间、错误码和结果。
- 支持账号池选择、分配策略、并发上限、任务暂停/继续/取消、失败目标重试。
- 创建时检查租户归属、目标重复、账号可用性和群组类型；服务端再次校验，不能信任前端传入的租户或账号关系。
- 已加入目标跳过；公开群组按 username/peer 解析；私密群组使用有效邀请链接流程；需审批的目标标记为待审批，不伪报成功。
- 遵守 Telegram 返回的 FloodWait/平台限制，不通过换号、换代理或高频重试规避限制。

## 4. 冷却与自动恢复

- 将平台返回的等待秒数持久化为 `next_attempt_at`，使用数据库时间/UTC 统一计算。
- 冷却期间账号不领取新目标；其他符合条件的账号可继续执行其合法分配目标。
- Worker 周期性扫描到期冷却账号/任务，重新检查会话授权和账号状态；确认可执行后自动恢复队列，无需租户手动点击。
- 到期后仍受限则按最新服务端等待时间再次延期；登录失效、封禁或需人工处理的异常不得自动解封。
- 任务重启、Worker 重启后仍能恢复；领取目标采用事务/租约/幂等键避免重复执行。

## 5. 监控系统

- 租户视图：账号健康、任务总览、成功/待审批/冷却/失败/待执行计数、单目标时间线、异常原因。
- 管理员视图：Worker 心跳、队列积压、任务延迟、失败率、数据库/Redis依赖状态。
- 告警可确认/关闭并保留审计；不得泄露其他租户账号、群组或任务信息。
- 前端所有状态、空态、加载态、错误提示中文化；桌面与移动端均可操作。

## 6. 必须验收的场景

1. 跨分页勾选多个群组，只生成一个批量任务且目标数量准确。
2. 同一批次包含公开群组和有效私密邀请链接。
3. 已加入、失效链接、需审批、FloodWait、登录失效分别得到正确状态。
4. FloodWait 到期后 Worker 自动重新检查并恢复；不要求租户手动继续。
5. Worker/API 重启后任务不丢失、不重复加入、不丢失冷却截止时间。
6. 暂停、继续、取消和失败重试均按租户权限生效。
7. 多租户隔离测试覆盖列表、详情、批量操作、监控和导出。
8. Go 后端测试、前端 lint/typecheck/build、数据库迁移检查全部通过。

## 7. 实施约束

- 先审计现有实现和迁移，复用已有表/接口，避免平行造轮子。
- 每个闭环提交独立可审查 PR；所有功能完成后统一做集成回归。
- CI 失败、未执行的测试、未验证的 Telegram 真机流程必须明确标注，不以“代码已提交”代替验收。
- 不在本次实现中加入绕过 Telegram 限制的机制。
