# Go Backend

TG账号管理系统 API。需要 Go 1.23+、PostgreSQL 和 Redis。复制仓库根目录 `.env.example` 为 `.env`，填写数据库、Redis、管理员初始化和加密密钥等配置；不要提交 `.env`。本地运行前执行 `set -a; source ./.env; set +a`，再进入 backend 目录执行 `go mod tidy` 和 `go run ./cmd/api`。部署时应通过平台 Secret 或容器 env_file 注入同一组变量。

## 超级管理员初始化
首次启动前设置 SUPER_ADMIN_USERNAME 和至少 16 字节的 SUPER_ADMIN_PASSWORD。数据库中没有超级管理员时，服务会创建一个；已有超级管理员时不会覆盖。初始化后建议从部署环境移除这两个环境变量。

## 认证接口
- POST /api/v1/auth/register：注册租户管理员，创建待激活租户。
- POST /api/v1/auth/login：签发随机 Bearer Token，数据库只保存令牌摘要。
- POST /api/v1/auth/activate：提交一次性卡密。
- GET /api/v1/auth/me：当前用户。
- POST /api/v1/auth/logout：退出当前设备。
- POST /api/v1/auth/password：修改密码并撤销其他设备会话。

## 超级管理员接口
所有接口均要求超级管理员 Bearer Token。
- POST /api/v1/admin/cards：批量生成卡密；请求字段 count、duration_days。明文卡密仅在创建响应中显示一次。
- GET /api/v1/admin/cards?limit=100：查看卡密状态，不返回明文。
- POST /api/v1/admin/cards/{id}/disable：禁用未使用卡密。
- GET /api/v1/admin/tenants?limit=100：查看租户。
- PATCH /api/v1/admin/tenants/{id}/status：设置 active 或 disabled。
- PATCH /api/v1/admin/tenants/{id}/account-limit：设置账号上限。
- PATCH /api/v1/admin/tenants/{id}/expiry：设置租户到期时间，字段 expires_at 使用 RFC3339。

禁用租户后业务请求会被订阅检查拦截。恢复租户不会自动恢复后台任务；后续 Worker 必须保持任务暂停，等待人工确认后恢复。

## 安全边界
Telegram Session 和代理凭据必须加密存储，不得通过普通 API 返回。生产环境必须使用 HTTPS 和密钥管理。业务查询必须从认证上下文取得 tenant_id，不能信任客户端传入。当前仍需补充限流、审计、租户数据访问层和自动化测试，不能直接视为公网生产就绪。

## Telegram 账号 API（基础版）
所有接口使用租户 Bearer Token，并从认证上下文确定租户，不接受客户端指定 tenant_id。
- POST /api/v1/accounts：导入单个账号，字段 phone、display_name、group_name、session、proxy。Session 与代理 JSON 使用 AES-256-GCM 加密后保存；新导入账号状态为 pending，待后续 MTProto Worker 验证连接。
- GET /api/v1/accounts：列出当前租户账号，不返回 Session 或代理密文。
- PATCH /api/v1/accounts/{id}/group：修改账号分组。
- DELETE /api/v1/accounts/{id}：删除当前租户账号。

账号创建时在事务中锁定租户行并检查 account_limit，避免并发请求突破上限。账号读写通过事务级 tenant scope 配合 PostgreSQL RLS。
生产环境必须设置 SESSION_ENCRYPTION_KEY：生成 32 字节随机密钥并以 Base64 或 64 位十六进制字符串配置。密钥应放入密钥管理服务或受保护的部署 Secret，不能提交到仓库。密钥轮换需先实现版本化解密迁移，不能直接替换旧密钥。


## Telegram MTProto

Telegram connectivity is standardized on `github.com/mtgo-labs/mtgo`; device identities are generated by `github.com/mtgo-labs/device-manager` and persisted per account. The current module requires Go 1.26.2 or newer. Configure `TELEGRAM_API_ID` and `TELEGRAM_API_HASH` from my.telegram.org before enabling Telegram login workers. Device model and iOS system version are generated deterministically from the account ID; language defaults can be overridden with environment variables. The API credentials and account sessions must never be exposed to tenant-facing API responses.


## Go verification

GitHub Actions runs `go mod tidy`, `go test ./...`, `go vet ./...`, and builds the API using Go 1.26.2. The workflow is the source of truth for dependency resolution and compilation status.

## 账号代理管理 API

代理统一归属账号管理模块，所有接口均使用租户 Bearer Token；租户 ID 只从认证上下文取得。
- GET /api/v1/proxies：列出当前租户代理，不返回密码或密文。
- POST /api/v1/proxies：创建代理，字段 name、protocol（socks5/socks4/http/https）、host、port、username、password。
- PUT /api/v1/proxies/{id}：更新代理配置；password 为空时保留原密码。
- DELETE /api/v1/proxies/{id}：删除未绑定账号的代理；仍有账号使用时返回 409。
- POST /api/v1/proxies/{id}/check：执行最多 4 秒的 TCP 端点连通性检查。该检查只确认目标端口可建立 TCP 连接，不代表代理认证或 Telegram 登录验证成功。
- PATCH /api/v1/accounts/{id}/proxy：绑定代理，传入 proxy_id；传空字符串解除绑定。绑定关系和代理数据均按租户隔离。

代理密码单独使用 SESSION_ENCRYPTION_KEY 进行 AES-256-GCM 加密。Worker 在租户作用域内读取绑定代理并在内存中解密；账号旧版内嵌代理配置仍兼容。账号列表只返回 has_proxy，不返回凭据。

## 跨账号消息汇总 API

消息由独立 Telegram Worker 通过 MTGo 新消息事件接收，并在写入数据库前执行两层过滤：
1. 固定规则：只收普通私聊的对方来信；群组/超级群/论坛只收明确回复当前账号本人消息的内容；排除机器人私聊、广播频道、自己发出的消息和其他事件。
2. 租户可配置规则：启停汇总、选择账号、选择群组/聊天 ID、启用文字或媒体、关键词匹配。未配置时默认收集所有账号的符合固定规则的文字和媒体消息。过滤在入库前执行，不是只隐藏列表结果。

接口（租户 Bearer Token）：
- GET /api/v1/groups：返回账号已观察到的群组/频道资料，支持 chat_type=group|channel、q 名称/用户名搜索，以及 limit/offset 分页；只读当前租户数据。
- GET /api/v1/messages：默认只返回未处理消息；支持 limit、offset、include_processed=true。
- GET /api/v1/messages/chats：按账号和聊天分组，返回聊天标题、用户名、成员数、认证标记、未处理数量和最近一条消息。
- GET /api/v1/messages/events：SSE 实时事件流，使用 Bearer Token 认证；连接后推送 `message` 事件（JSON 包含 `type`、`account_id`、`chat_id`、`message_id`、`created_at`），每 25 秒发送心跳。浏览器端请用支持 Authorization 请求头的 fetch 流式读取，不要把长期令牌放进 URL。事件通过 Redis 按租户隔离发布，数据库仍是消息事实来源；断线重连后应重新拉取未处理列表以补齐遗漏。群组/频道资料按租户/账号/聊天隔离缓存：Worker 观察到私聊、群组或频道事件时更新必要的聊天元数据，不受消息正文采集开关、关键词或“仅收回复本人消息”规则影响；这些规则仍严格控制消息正文入库。资料库只包含账号实际观察到的聊天，不枚举未知对话，也不代表完整 Telegram 群组目录。
- PATCH /api/v1/messages/{id}/processed：标记已处理，消息从默认未处理列表消失。
- GET /api/v1/messages/settings：读取当前租户收集条件。
- PUT /api/v1/messages/settings：更新条件。字段 enabled、include_all_accounts、account_ids、chat_ids、include_text、include_media、keywords。include_all_accounts=false 时仅收 account_ids 中账号；chat_ids 非空时仅收指定聊天；keywords 非空时文字需命中任一关键词。
- POST /api/v1/messages/{id}/reply：提交对该条汇总消息的回复，字段 text，返回 202 和 reply job ID；实际发送由独立 Worker 执行。
- GET /api/v1/message-replies/{id}：查询回复任务状态（pending、processing、sent、failed）、尝试次数和 Telegram 返回的消息 ID。

消息列表保留 account_id、chat_id、message_id、chat_title、reply_to_message_id。回复任务采用 PostgreSQL 持久队列、租户 RLS、5 分钟处理租约和最多 5 次失败重试；Worker 使用对应账号的 MTProto 客户端发送 Telegram 原生回复，并回写 Telegram 消息 ID。Worker 崩溃后过期租约可重新领取；发送成功但回写数据库失败时存在极小概率重复发送，因此当前是可恢复的至少一次投递语义，不承诺严格 exactly-once。群组资料缓存已接入实时消息。Worker 每 5 分钟对每个在线账号最近活跃的最多 20 个已知聊天回查最近 50 条消息，补齐短暂断线期间遗漏的记录；仍未发现过的新聊天不会自动枚举，完整历史导入需后续单独实现。历史回填复用相同固定规则和租户筛选，群组只收明确回复当前账号本人消息的内容。


## 关键词自动处理与媒体相册

关键词规则和任务均按租户隔离，Telegram 发送由独立 Worker 使用 MTGo 执行。支持文字、原生联系人卡片、单素材媒体及相册动作。
- 关键词规则接口：GET/POST /api/v1/keyword-rules、PUT/DELETE /api/v1/keyword-rules/{id}；GET /api/v1/keyword-rules/matches 查询匹配记录。规则中的账号过滤和素材引用必须属于当前租户。
- 媒体库接口：GET/POST /api/v1/keyword-media-assets、GET/DELETE /api/v1/keyword-media-assets/{id}。上传限制为单素材 20 MiB，按租户 SHA-256 去重。
- 相册动作使用 action_type=media_album，media_album_items 按顺序包含 2-10 个 {asset_id,media_type,caption}；支持 photo/video 混合或纯 document，不允许 document 与 photo/video 混合。
- 每个相册素材必须属于当前租户，素材被规则或任务引用时禁止删除；API 校验和 PostgreSQL 触发器双重验证素材归属、重复项、媒体类型和 caption 长度。
- 单项最大 20 MiB，相册总量最大 100 MiB；每项 caption 最多 1024 个 Unicode 字符。MTGo 上传全部素材后一次性提交媒体组，返回的全部 Telegram message ID 会保存到 keyword_action_jobs.telegram_message_ids；旧 telegram_message_id 字段保留为首条消息 ID兼容字段。
- GET /api/v1/keyword-actions 返回任务状态、重试次数、错误信息、相册素材清单及完整 telegram_message_ids；POST /api/v1/keyword-actions/{id}/{action} 支持 pause、resume、retry；任务状态支持 pending、processing、sent、failed、paused。
- Worker 对离线账号释放租约并延迟重试，租户停用时暂停任务，Telegram FloodWait 进入账号冷却；普通失败最多重试 5 次。
- 任务采用至少一次投递语义：若 Telegram 已接受发送但数据库结果回写失败，租约过期后可能重复发送；Telegram MTProto 媒体组接口不提供本项目可用的端到端幂等键，因此不承诺 exactly-once。


## Telegram 账号资料与头像
账号资料变更采用持久化批量任务，任务按租户隔离并支持查询、重试、恢复和取消；实际 Telegram 写入由 MTGo 运行时执行。头像上传通过 multipart 的 `photo` 字段提交，`account_ids` 为 JSON 字符串数组，单文件最大 5 MiB，仅接受可完整解码的 JPEG/PNG，最大 4096×4096 且不超过 16MP；上传同一头像可应用于 1-20 个当前租户账号。SVG、WebP 和伪造 MIME/扩展名内容不接受。

- POST `/api/v1/accounts/profile-updates/photo`：上传头像并为指定账号创建批量任务，返回 202、batch_id 和 jobs。
- POST `/api/v1/accounts/profile-updates`：批量提交姓名、简介及用户名资料更新任务。
- GET `/api/v1/accounts/profile-updates`：按 batch_id/status 分页查询任务。
- POST `/api/v1/accounts/profile-updates/{id}/retry|resume|cancel`：管理单个资料更新任务。
- GET `/api/v1/accounts/{id}/profile`：读取当前在线 MTGo 会话的 Telegram 自身身份（用户 ID、用户名、姓名、手机号）；先验证账号属于当前租户。账号离线时返回冲突，不返回缓存冒充实时资料。
- GET/PUT `/api/v1/accounts/username-generation-settings`：读取和保存租户用户名生成规则；该设置是本系统的生成策略，不代表 Telegram 已接受用户名。

用户名最终可用性由 Telegram 服务端裁定；客户端格式校验不能代替服务端唯一性检查。Telegram FloodWait、用户名占用及其他 MTProto 错误由任务执行结果记录，按任务策略重试；不要高频重复提交。当前实时资料读取使用 MTGo 的已授权 self User 对象；Telegram 的完整隐私/简介字段不在该接口的承诺范围内。
